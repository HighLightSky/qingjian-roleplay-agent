# 14｜剧情图生成与视觉上下文方案

> 2026-10-24。剧情图功能设计稿，尚未实现；当前聊天图片数量配置已统一调整为十张。以当前代码及 [11-后端编排与缓存](./11-后端编排与缓存.md)、[12-辅助上下文与模型调用策略](./12-辅助上下文与模型调用策略.md) 为基础。外部调用协议以 [13-生图服务 API](./13-生图服务API.md) 为准。本方案明确调整了历史图片重复观察规则，实施时需要同步更新相关旧文档。

## 1. 本版确定的产品行为

1. 每轮主模型在正常回复后，用同一次流式调用生成一个画面计划和中文分层生图提示词；前端默认折叠。
2. 用户点击“生成剧情图”才调用生图服务。普通聊天不自动生图，提示词完成后立即进入本轮状态整理，不等待用户操作或图片结果。
3. 每次生图必须携带当前会话角色快照中的身份原图。没有配置身份图或必需原件缺失时，本轮不能生图，正常聊天沿用现有规则。
4. 正文前的选图阶段复用现有选图调用，范围扩展到当前会话的上传图、生成图及会话角色照片。上传、正文选图与生图参考图的应用数量上限统一为十张，各请求分别计算。正文 LLM 不声明固有的图片张数上限，仍受实际上下文 token 预算约束。
5. 新上传图片直接进入正文原图上下文，不依赖图片摘要，也不等待选图模型选中。
6. 已有观察的上传图、角色照片不因再次选中而重新整理；生成图使用提示词末尾的“画面摘要”，不自动执行观察。
7. 参考图必须说明用途。身份、服装、环境、姿态可以分别取自不同图片，不把某张图的全部属性一起继承。
   传给生图服务时，第一张编辑底图和角色身份图使用原始图像字节；其他参考图可使用合适的缩略图或压缩版本。
8. 图片继续使用浏览器 IndexedDB 资产体系和后端临时缓存；不增加服务端长期图库，不实现模型推理或 ComfyUI 工作流。
9. 第一版沿用“一名主角色、一张角色身份照”的角色模型。配角可出现在画面中，但没有独立身份照绑定时，不承诺其跨图身份一致。

## 2. 当前实现核查

### 2.1 新上传图片不会因为缺少摘要而漏进正文

目前的调用关系为：

- ImageValidationService.newIds() 从本轮 input 的图片内容块提取资产编号。
- requiredIds() 将本轮附件与首次无观察的角色照片合并为必选图片。
- selectableCatalog() 从历史候选中排除这些必选图片。
- ChatDispatchService.Task.execute() 将必选图片与选中的历史图合并，从 ImageCache.Lease 读取真实载荷。
- PromptBuilder.appendVisualContext() 把本轮附件附在真实的本轮输入中。

所以，新上传图片“不参加历史图选择”是正常行为，不等于“不提供给正文”。首次使用没有历史图片时，也可以跳过选图调用，直接携带新图生成正文。

历史上传图同样不强制要求已有观察：selectableCatalog() 接受具有 MessageSource 的图片。其目录可以使用上传时的文字和来源信息，只是此时语义召回能力弱于有观察的图片。

### 2.2 整理器目前会重复观察已知图片

当前 ChatDispatchService 把正文 prepared 上下文的全部 imagePayloads 继续交给整理器；StateController 的手动重试也重新装入全部选中图片。

StateUpdateMaterial、StateUpdatePromptBuilder 和 StateUpdateResponseSchema 按全部实际载荷建立观察任务；StateUpdateService.observations() 要求逐张覆盖，并在旧观察版本上加一。因此同一张图连续被选中时，会重复传给整理模型、重复生成观察、重复推进版本。

本版修改的是“整理器需要处理哪些原图”，不是削弱正文对原图的访问能力。

### 2.3 现有资产与执行边界

- 角色照片通过 appearancePhotoAssetId 绑定角色，会话保存创建时的角色快照和 profileVersion。
- Story 已管理地点、时间、角色状态、在场人物、物品等；摘要、历史、记忆和目标已有统一上下文链路。
- buildCatalog() 目前只扫描用户消息图片和角色照片，需要显式接入生成记录。
- 资产按 SHA-256 去重；imgN 是浏览器全局资产编号，不是远端 URL。
- ImageCache 目前接收、校验并临时缓存原图；LLM 输入通过 data URL 提供，生图接口需要真实文件字节。
- ModelGate 的一个名额覆盖选图、正文和整理；生图必须使用独立执行名额。
- 前端 tool-call 记录是编排器过程的展示，不代表已经存在通用的模型函数调用框架。本版直接扩展现有编排。

## 3. 总流程与职责

~~~mermaid
flowchart TD
    A[读取会话快照、剧情、视觉状态、摘要和图片目录] --> B[预算预检与图片缓存补齐]
    B --> C[选图模型：只读文字目录]
    C --> D[正文模型：读取必选与选中原图]
    D --> E[流式台词与描写]
    E --> F[同一次调用输出画面计划、中文提示词和画面摘要]
    F --> G[立即执行状态整理]
    F --> H[用户点击生成剧情图]
    H --> I[补齐最终参考图并启动独立生图任务]
    I --> J[外部图像编辑 API]
    J --> K[浏览器保存生成原图、摘要及来源]
    K --> L[后续轮次目录与连续性参考]
~~~

选图模型负责召回；正文模型负责结合实际图片与本轮故事确定画面、参考用途和提示词；整理器负责提交有对话依据的当前状态。生图服务只接收最终提示词和有序文件列表。

“生成提示词”与“执行生图”是两个独立过程。图片生成期间可以继续后续聊天；选图、正文和整理仍遵守现有 LLM 串行名额。并发调度解耦不等于承诺底层共享 GPU 不会影响速度。

## 4. 数据模型：出处、事实与目标分开

### 4.1 资产出处

ImageAsset 增加 creationOrigin，取 uploaded 或 generated，表示该资产首次由用户上传入库，还是由生图服务返回入库。角色照片也属于用户上传，其身份参考用途仍由 CharacterPhotoSource 表达。

同一字节内容后来以其他方式进入应用时，继续复用资产并保留首次出处。一次上传行为和一次生成行为分别由来源记录表达，不能为了改变 creationOrigin 覆盖已有资产或复制相同原件。

VisualSource 在现有 message、character_photo 之外新增 scene_generation：

~~~ts
type SceneGenerationSource = {
  type: "scene_generation";
  generationId: string;
  planId: string;
  messageId: string;
  seq: number;
  sceneId: string;
};
~~~

生成图片绑定真实 assistant 回复与生成记录，不伪装为用户附件，不增加用户的 uploadIndex。一个资产可同时具有用户上传和生成来源；来源与描述的作用域仍为当前会话。

### 4.2 两类图片描述

| 字段 | 来源 | 能说明什么 |
| --- | --- | --- |
| observation | 整理器首次读取上传原图或角色照片 | 原图实际可见内容及不确定项 |
| generationDescription | 已完成生图所用提示词的画面摘要及目标属性 | 生成要求中的画面内容，没有经过图像核实 |

generationDescription 包含 summary、planId、generationId；服装、环境等结构化信息引用对应计划的 target，不再复制一份长描述。它不写入 visualObservations，不具有“观察版本”，也不声称已辨认图片文字。

目录可同时提供两类描述。真实观察、当前用户纠正和失效标记优先于生成要求；两者冲突不能抹掉其来源。只有提示词、尚未成功生成的记录不进入图片目录。

同图在另一个会话作为用户上传时，不能利用资产哈希跨会话读取私有生成计划或观察；该会话没有可用描述时仍按首次上传图处理。

### 4.3 当前剧情与视觉状态

继续保留 Story 作为剧情事实来源，不让生成成功回调改写剧情。为避免把详细服装挤进现有简短 characterState，Session 增加轻量 visualState 和 visualSources：

~~~ts
type VisualState = {
  outfit: string;
  hairstyle: string;
  accessories: string[];
  appearanceChanges: string[];
};
~~~

只记录当前剧情明确成立、会跨轮持续的视觉事实，例如“白色长袖棉布连衣裙”“发髻已散开”“左手缠绷带”。无已知值使用空字符串或空数组，表示未知，不自动填成“默认服装”。

- 地点、故事时间、在场人物及关键物品仍分别归 Story 原字段。
- characterState 保留整体身体、情绪与剧情状态；详细服装以 visualState 为准，不维护两套独立服装结论。
- 临时手势、瞬间表情、机位、画风只进入本轮 target；不作为永久状态继承。
- 天气、环境光线与本轮具体环境进入 target；延续时参考上一适用画面的 target，当前剧情与时间变化优先。
- visualState 由现有整理器通过 visualChanges 提交，与 Story 变更共用 session.stateVersion、人工修改保护和同一事务。
- 未生图的普通对话也能更新 visualState。图片成功、失败或被否定都不直接修改它。

### 4.4 画面计划 SceneImagePlan

增加 sceneImagePlans 仓库，按 session 和来源消息索引。计划保存：

| 字段 | 含义 |
| --- | --- |
| id、sessionId、assistantMessageId | 稳定计划编号和归属 |
| sourceSeq、sourceCheckpointVersion、profileVersion | 来源回复与角色快照版本 |
| sceneId、previousPlanId、continuity | 视觉场景标识、前序画面及延续关系 |
| target | 当前画面的主体、服装、动作表情、环境、光线、材质、构图和风格 |
| referenceImages | 有序资产列表、角色用途、适用属性与来源版本 |
| prompt、summary | 发给服务的完整中文提示词及末尾画面摘要 |
| fingerprint | 参考内容哈希、有序用途、target、prompt、角色快照与来源版本的指纹 |
| status、error | streaming、ready、reuse、unavailable、invalid |

target 是该张图片的绘制目标，不是新的剧情事实表。当前用户只要求“画成红裙”而没有在剧情中换装时，可以生成红裙画面，但不能把红裙写入 visualState。

continuity 使用 new_scene、continue_scene、restage 三种语义：新视觉场景、延续当前场景、同一剧情下另取构图。sceneId 由应用分配，模型仅输出关系和已有计划引用；不让模型编造存储 ID。

同一轮正文包含多个动作时，默认画回复结束处仍成立的一个可见时刻；用户明确指定时刻则遵循用户。不要把先后发生的动作合成不可能同时存在的画面。

来源版本必须对应这次正文成功完成后的检查点。发送聊天任务时，由前端在 assistant 消息元信息中提供预期完成版本，后端据此绑定计划；前端只在相应正文终态已保存后把计划提交为 ready。不能先绑定 pending 版本，再让正文正常完成使计划立即过期。

### 4.5 生成记录 SceneGeneration

增加 sceneGenerations 仓库，记录 id、sessionId、planId、来源消息版本、sceneId、任务状态、生成资产引用、错误、时间及 supersedesGenerationId。

任务状态与图片有效性分开：

- status：pending、running、succeeded、failed、cancelled、unknown。
- referenceStatus：eligible 或 rejected，另存中文 rejectionReason。
- succeeded + eligible 表示可供选图考虑，不表示经过图像核实。

默认成功结果可作为候选；用户“这张图有误／不用这张”后排除其生成来源，不删除原图。用户若明确重新上传相同原图作为参考，该新上传行为仍有效，不能因历史生成记录被否定而全局封禁资产。

## 5. 参考图如何选

### 5.1 两次收敛，只有一次选图模型调用

正文前选图决定“本轮主模型看哪些原图”；正文结束时，主模型在同一次输出中给出“实际生图使用哪些参考图”。这不是第二次模型请求。

选图模型不接收原图，输入继续使用有界的近期对话、阶段摘要、Story、visualState 和精简图片目录。目录新增生成摘要的来源类型、目标属性、场景关系及否定标记，排除哈希、文件体积、存储 ID 等无语义字段。

实际图片数量继续由 requiredIds() 和剩余 slots 控制，按 assetId 去重。候选文字目录数量不受十张实际图片名额限制，已有分批预算机制保留。十张是应用本次统一采用的资源策略，不是 LLM 模型本身的固有限制；修改策略仍通过服务端配置。

### 5.2 候选范围与资格

| 图片 | 是否进入正文前历史候选 |
| --- | --- |
| 本轮新上传图片 | 不参加历史选择，直接提供原图 |
| 首次无观察的角色照片 | 现有必选机制直接提供 |
| 已有观察的角色照片 | 按本轮聊天语义选择；生图时仍始终必带 |
| 本会话历史上传图片 | 可选，有无观察均可，保留上传文字和顺序 |
| 本会话成功生成且 eligible 的图片 | 可选，使用 generationDescription，不要求 observation |
| 正在生成、生成失败、被否定的生成来源 | 不进入生图连续性候选 |
| 原件缺失项 | 不可选，沿用现有缺图声明 |
| 其他会话的私有图片 | 不可选 |

生成图尚未有 observation 不能阻止其进入 selectableCatalog()。生成摘要本身就是这类图片的语义检索材料。

### 5.3 按用途判断相关性

1. 身份：当前会话主角的身份原图是最终生图必选项，不能被模型替换为某张历史生成图。
2. 连续性：优先考虑剧情位置相关、用户未否定的最近有效场景图；最近按来源回复 seq 判断，不按任务完成时间。
3. 服装：先用当前明确状态的文字；特殊图案、剪裁等确有必要时才加入精确参考。
4. 环境：指定复现某个具体房间、建筑或布局时选图；普通“花园”“咖啡馆”通常只需文字。
5. 姿态与道具：精确造型、持握方式、空间关系难以表达时才添加。
6. 同一张图可承担多个用途，但明确列出允许参考的属性；不为了多用途重复上传。

生成摘要标记为“来自生成要求，未核实”。正文实际看到选中原图后，可以拒绝错误参考、限制继承属性，或在提示词中明确纠正。第一版不为漏选候选追加串行看图请求，也不承诺仅凭文字目录可以精确召回未记录的细节。

### 5.4 最终清单与统一十张上限

正文主模型只能从本轮实际看过的图片中选最终场景、服装、姿态和道具参考。身份原图是例外：即使本轮没有重看，它仍由应用按会话快照固定加入生图。

正文可以看十张附件，生图却只选其中九张再加身份图；本轮新图对正文必选，不意味着对生图必选。若十张非身份图都被认为不可缺少，应把计划标记 unavailable 并说明名额冲突，不静默丢掉必需图，不影响正文。正文自身仍按统一应用限制计算必选照片、附件和历史图的去重总数，首次照片占用一个名额。

上传、预算预检、正文选图、整理和压缩的数量限制统一读取 roleplay.vision.max-images，当前值为 10。最终生图上限为 min(现有 VisionProperties.maxImages，生图服务支持数量)，当前同为十张；应用不使用远端“多余图静默丢弃”的行为。不在 LLM 客户端另写一个模型上限，也不为凑满十张而选择无关图片。

当前链路核查结果：配置文件此前为五张，VisionProperties 字段另有四张默认值，前端 DEFAULT_LIMITS 也有四张默认值。后两项重复数量默认值已移除，前端上传继续读取 /api/capabilities；预算、正文前选图、严格 schema、结果校验和压缩分批都已读取后端配置，不需要各自改写数量常量。测试夹具和模拟能力接口同步使用十张，覆盖十张通过和第十一张拒绝。

### 5.5 第一张是编辑目标，身份图不一定排第一

外部 API 的第一张图片既是编辑目标，又决定输出画幅和尺寸；其余图片才是参考图。因此固定“身份图永远 image1”不适合所有场景。

| 任务 | 第一张 | 后续图片 |
| --- | --- | --- |
| 初次生成 | 身份图 | 必要的服装／环境参考 |
| 延续上一幕且布局适用 | 上一幕场景图 | 身份图，再加必要参考 |
| 换装但保留环境构图 | 有效场景图 | 身份图、必要的新服装图 |
| 新地点或原图布局不适用 | 通常身份图 | 按需服装／环境图，明确重建构图 |
| 用户指定某上传图作为编辑底图 | 指定底图 | 身份图和其余必要参考 |

先确定编辑目标，再放入尚未出现的身份图，最后按必要性排列其他参考。去重后同图合并角色用途。应用在生成计划时冻结这个顺序，不在点击生图时重新排序。

没有独立宽高参数。第一版展示预期画幅来自哪张图，不声称支持任意分辨率；需要新画幅时须另行设计明确的输入裁剪能力。

### 5.6 生图文件版本：底图与身份保真，其他参考减量

参考清单冻结资产顺序和用途之后，应用按用途准备传输文件，模型不需要决定具体编码格式：

| 参考图用途 | 传输版本 | 说明 |
| --- | --- | --- |
| 第一张编辑底图 | 原图 | 保持原始尺寸和字节，输出画幅仍由它决定 |
| 角色身份参考图，无论排第几 | 原图 | 保留面部细节，不使用图库缩略图或二次有损压缩 |
| 其他服装、精细道具参考 | 压缩参考图 | 保留足够的图案和材质细节；默认最长边上限 1024，JPEG 质量 0.85，透明图使用合适的 PNG 编码 |
| 其他环境、粗略姿态参考 | 缩略图或压缩参考图 | 现有缩略图足以表达用途时直接复用；细节不足时从原图生成上述压缩版本 |

同一资产兼具底图／身份与其他用途时，原图规则优先，去重后只传一次。其他图片已经足够小且满足预算时可以直接使用原文件，不为压缩而放大或重新编码。压缩只改变传输版本，不改变 assetId、参考用途、顺序和 <imageN> 映射。

压缩参考图参数集中配置为 referenceMaxEdge 和 referenceJpegQuality，前端读取能力接口；生成的派生文件按原图哈希、参数与算法版本缓存。图库现有 256 像素缩略图不自动成为所有辅助参考的默认输入，复杂服装图案应使用细节更充分的压缩图。

原件始终保留，压缩文件记录自己的哈希、尺寸、字节数和 sourceSha256。不能将压缩字节按原图哈希上传到缓存，也不能把缩略图尺寸当作底图的真实尺寸。

底图或身份原图超出远端单图、像素或总量限制时，本次生图明确不可执行；不偷偷压缩它们。先固定原图占用，再根据剩余预算缩小其他参考；仍不满足条件则明确报错，不擅自删除参考。原件缺失时也不以缩略图代替。

此策略减少上传字节和辅助参考的像素处理成本；实际推理耗时还取决于底图分辨率、队列和模型，不保证按压缩比例缩短。它只约束生图服务，正文仍按现有语义实际查看选中图片，不因为某张图在生图时属于辅助参考，就自动只向 LLM 提供图库缩略图。

## 6. 中文提示词如何写

### 6.1 固定层次

完整提示词由八段组成：

1. 参考图说明。
2. 主体。
3. 环境。
4. 光线。
5. 材质。
6. 构图。
7. 风格。
8. 画面摘要。

只有实际存在的参考图才使用对应的 <imageN>。参考说明强调“从哪张图取哪些内容”；后续段落用具体可见描述明确本图要呈现什么。当前剧情用于推导画面，不写入“她刚刚……所以现在……”等事件解释。

主体段描述人物、服装、动作、身体朝向、目光与可见表情。身份依靠原图，不用长篇五官形容词替代。材质写实际需要呈现的织物、金属、木材等表面特征，不为了填段落增加道具或衣饰。

未指定且无连续性依据的风格，使用克制的统一表达；不得随意增加职业、年龄设定、重要服装设计或剧情物品。缺少会显著影响结果的信息时，计划不可执行并给出具体原因。

### 6.2 示例：场景底图、身份图和服装图

假定实际上传顺序是上一幕、身份图、复杂服装图：

~~~text
参考图说明：
以 <image1> 为编辑底图，保留房间布局、窗户位置和木桌。
主体为与 <image2> 相同的人物，保持面部身份与稳定的发型特征。
主体穿着 <image3> 中的白色长袖连衣裙，保留领口剪裁和袖口刺绣；
服装以 <image3> 为准，人物姿态按下文重绘。

主体：
女子站在木桌右侧，身体朝向窗户，脸转向画面左前方。
右手轻扶桌沿，左臂自然垂下，嘴角略微上扬。
白色裙摆垂至脚踝，服装完整呈现。

环境：
木质房间，窗户位于人物左后方，木桌位于画面左侧。
窗外可见浅绿色树叶，背景保持简洁。

光线：
柔和晨光从左后方窗户进入，脸部有自然补光，阴影边缘柔和。

材质：
连衣裙为细密棉布质感，袖口刺绣清晰；木桌保留自然木纹。

构图：
竖幅全身景，人物位于画面右侧三分之一处，视线高度平视，
头顶与裙摆下方保留少量空间。

风格：
自然写实摄影，肤色自然，清晰呈现衣料和面部，背景适度虚化。

画面摘要：
木质房间中，女子穿白色长袖刺绣连衣裙站在木桌右侧，右手扶桌，
侧身朝窗并转脸微笑；左后方柔和晨光，竖幅平视全身构图，自然写实摄影。
~~~

示例中的晨光、裙长、构图等须已有本轮要求或合理画面依据，不作为每轮硬编码默认值。如果只有一张身份图，只说明 <image1>，不生成空位、不引用 <image2>。

### 6.3 摘要直接取最后一段

画面摘要必须自包含：具体人物、服装、动作表情、环境、光线、构图和风格。不得写“同上一张”“服装见图三”等无法独立检索的表达，也不包含图片编号、内部资产编号、事件经过或不可见心理。

它是同一轮主模型输出的一部分，生图成功后直接保存为 generationDescription.summary。不再次调用 LLM 压缩提示词，不解析参考图说明来猜画面，不把整个聊天记录作为摘要。

服务收到的最终 prompt 包含画面摘要；资产保存的摘要必须来自实际提交版本，不能来自后来编辑或重生成的其他计划。

## 7. 主模型输出与流式协议

### 7.1 继续使用已有分段框架

扩展 SegmentStreamParser，但前端 Message.segments 仍只存 dialogue 和 narration。新增画面内容单独通过事件和 sceneImagePlans 保存，避免 plainText()、复制正文、historyText()、摘要及记忆整理混入绘图指令。

建议模型尾部协议：

~~~text
[台词]……
[描写]……
[画面计划]{"action":"create","continuity":"continue_scene","previousPlanId":"本次材料中提供的计划别名","target":{},"referenceImages":[]}
[参考图说明]以 <image1> 为编辑底图……
[主体]……
[环境]……
[光线]……
[材质]……
[构图]……
[风格]……
[画面摘要]……
~~~

上例 JSON 的空对象和空数组只演示协议位置，实际 create 计划必须完整且通过校验。已有计划 ID 使用当前请求内的短别名，服务端严格还原，不暴露模型无须处理的存储信息。

画面计划是单行 JSON，由 Jackson 在该行完整后解析，不手工截取 JSON、不剥离代码块。后续每段沿用现有行首标记识别和文本增量机制。未标记或协议非法的尾部不能降级为剧情描写。

referenceImages 是已按第 5.5 节规则排列的清单，每项提供 assetId、roles 和具体使用范围。服务端校验并冻结列表，不再插图、删图或改顺序；身份图若缺失，计划无效，而不是悄悄插入导致编号改变。

PromptBuilder 在模型输入中明确提供身份资产编号、可用参考范围、排序规则，以及“第 N 项对应 <imageN>”。模型按此规则写参考说明；SceneImagePromptAssembler 依据冻结列表构造最终提交版本并验证引用。

对外事件：

- scene_plan：已解析的计划元信息和状态。
- image_prompt_delta：段落名及文本增量。
- image_prompt_done：完整计划、最终提示词、摘要和指纹。
- image_prompt_error：本轮绘图内容无效的具体原因。

这些内容均进入 ChatDispatchService.Snapshot，重订阅先替换完整状态再应用增量。图片计划单独记录错误；有效正文仍正常完成并进行状态整理。

### 7.2 执行与复用

action 为 create、reuse、unavailable。默认可执行计划使用 create；已有画面与目标相同且无更新要求时可用 reuse，保留本轮画面描述与被复用记录，前端显示已有图，不自动调用服务。

ready 需要完整正文正常结束、完整提示词及合法参考清单；流未结束、取消或截断时不能点击生成。与“正文为空”的判断分开，只有提示词没有台词或描写不能算有效角色回复。

提示词 token 属于同一次正文调用的输出。需要为它保留输出预算，角色回复字数指引只计算台词与描写。状态整理仍在这一调用结束后开始；不承诺提示词本身零延迟。

第一版不提供直接修改含图片编号的自由文本提示词功能，避免修改后描述、摘要和清单失配。用户通过下一轮要求调整画面；后续若增加编辑器，应以完整计划为单位重新校验。

## 8. 修复重复观察

### 8.1 统一观察策略

新增 ImageObservationPolicy，供普通整理和手动重试共同使用。输入是冻结上下文、该轮正文实际使用的资产及当前已提交描述，输出 observationAssetIds：

| 图片情况 | 正文能否读原图 | 整理器是否附原图并新建观察 |
| --- | --- | --- |
| 本轮新上传、无观察且无本会话生成描述 | 能，必选 | 是 |
| 首次角色照片、无观察且无可用描述 | 能，沿用首次必选 | 是 |
| 历史上传图、没有观察 | 选中后能 | 是 |
| 任意上传图或角色照片、已有观察 | 必选或选中后能 | 否，复用已有观察 |
| 有本会话生成描述的生成图 | 选中后能 | 否，复用提示词摘要 |
| 同资产再次上传、已有本会话描述 | 能 | 否，只增加真实上传来源 |
| 原件缺失项 | 不能 | 否 |

观察缺失与读取失败不能混淆：需要首次观察的真实原件若损坏或校验失败，整理步骤明确失败，不用生成目标或空观察代替。

这里的“不重新观察”指不再由整理器重做描述；正文为了回答图片细节问题依然可以读取原图。第一版不新增自动刷新观察或重复补全摘要机制。

首次照片必选条件与该策略同步：已有本会话可用描述的照片不因为 observation 为空而被每轮当作首次照片。ImageValidationService.requiredIds() 与前端 requiredImageIds() 必须使用同一协议语义。这里不能只修改整理载荷，留下“永远没有观察，所以永远首次”的分支。

### 8.2 修改范围必须完整

1. ChatDispatchService 为正文保留完整实际原图集合，为整理单独构建仅含 observationAssetIds 的载荷。
2. StateController 手动重试使用相同 ImageObservationPolicy；不能仍把全部选中原图重新附入。
3. StateUpdateMaterial 同时提供已有文字描述与需要首次观察的实际 ID 清单。
4. StateUpdatePromptBuilder 只附首次观察原图，模板只列这些 ID。
5. StateUpdateResponseSchema 的 visualObservations 约束仅覆盖这些 ID。
6. StateUpdateService.parseResult() 依据观察目标清单判断是否要求数组；observations() 只接收这些 ID，无任务时输出空数组。
7. 前端只写入新返回的观察；复用观察的版本、摘要和时间戳不变。新增上传或角色用途来源由目录与引用记录合并，不依赖重新调用模型。

不再把“正文用过的图”直接当作“本轮需要整理的图”。观察目标集只定义一次，模板、schema、原图载荷和结果校验都使用同一集合。

压缩流程也要认识 generationDescription：生成图缺少 observation 是设计状态，不能触发压缩器补做看图。历史压缩引用该图时保留“来自生成要求”的描述类型及资产引用，不将其升级为实测事实。

## 9. 状态继承与避免混淆

### 9.1 属性优先级

服装、发型和饰品按照：本轮明确视觉要求 → 本轮已经发生的剧情变化 → 已提交 visualState → 最近适用生成计划的目标描述 → 角色默认设定。

从生成计划继承只是确定下一张画面的绘制目标，不能据此倒写剧情。无明确状态变化时复用已有目标，不每轮自行换装。

环境优先服从当前地点、时间和本轮要求；场景切换即重新确定背景，不能因为继续使用上一幕服装而保留旧房间。动作和表情按本轮选定时刻确定，不能机械继承上一张图的手势。

身份照片中的服装仅为原图事实，不等于角色默认服装，更不能覆盖剧情换装。受伤、湿发等已成立变化可以覆盖默认形象中的对应属性，同时保持身份。

### 9.2 整理器是持久状态的唯一自动写入者

StateDtos.ModelResult、Result 增加 visualChanges，字段范围只允许第 4.3 节的四项。人工修改来源保护、来源消息短编号、版本检查、允许修改字段投影与 Story 相同。

整理器从当前用户与正文的真实对话证据提取变化，不能把 SceneImagePlan.target 或 generationDescription 作为“事件已经发生”的新证据。选图和绘图计划只作为理解材料。

有已知但尚未提交的本轮换装时，正文模型直接按新状态生成计划；无需等待整理器完成才允许用户点击生图。计划冻结该轮目标，不依赖稍后修改的 Session 对象。

### 9.3 图片迟到、重生成与否定

- 第十轮图在第十一轮换装后返回，仍挂在第十轮，不改 Session.stateVersion，不覆盖新视觉状态。
- 生成资产与回复关联记录放在独立仓库；保存图片不增加正文 checkpointVersion，避免使同一轮尚未完成的整理来源校验失效。
- “当前图片”由来源 seq、未被否定、所属场景及适用属性共同决定，不用全局 lastImageId。
- 重生成结果通过 supersedesGenerationId 记录替代关系；旧图仍可查看，默认连续性优先新版本。
- 用户否定图片，只使其失去参考资格；如果同时明确“衣服应该是白色”，该文字才作为状态或本次画面要求的依据。
- 原图识别与生成摘要不同，默认不对生成结果做质量推断。正文看到原图或用户指出问题后再拒绝参考；不宣称能自动发现全部错误。

### 9.4 人工视觉要求与剧情分开

“画一张她穿红裙的图”默认是本次绘图要求；“她换上红裙”是剧情变化。“画成夜景”不会自动让故事时间变成深夜。

对于会实质改变结果的矛盾要求，主模型通过正常回复澄清，计划标记 unavailable；不额外启动一个澄清 Agent。

## 10. 生成服务接入

### 10.1 已确认接口

- 部署基址为 API 文档中的内网 HTTPS 地址，通过配置提供。
- POST /api/image/edit，Authorization 使用服务端独立配置的 Bearer Token，不复用聊天模型密钥、不写入前端或文档示例默认值。
- multipart 包含一个 UTF-8 prompt，以及按冻结顺序重复的 images 文件字段，不能使用 images[]。
- 响应是 HTTP 200、Content-Type 为 image/png 的完整 PNG 字节，不是 JSON、Base64 或下载 URL。
- 远端没有任务查询、进度或公开取消接口；一次请求生成一张图，随机种子不可指定。
- GET /ready 用于人工诊断或部署探测，不在每次生图前串行请求，也不把就绪当成队列可用。

新增 QwenImageClient，复用现有 HttpClient Bean。multipart 使用成熟组件，例如 Spring 的 FormHttpMessageConverter 编码，再交给 Java HttpClient 发送；由编码器生成并设置匹配的 boundary，不手工拼装文件分隔协议。

从 ImageCache.Lease 按清单读取第 5.6 节决定的文件版本及其真实 MIME：底图、身份图为原始文件，其他参考图可以为压缩文件。不能把 imgN、哈希字符串或 data URL 当作上传文件。新增二进制读取方法；LLM 原有 data URL 方法继续只服务其调用方。

### 10.2 限制不与聊天能力混用

生图服务输入默认单图 16 MiB、4,194,304 像素、最长边 8192；所有输入合计 16,777,216 像素，提示词最多 16,384 字符。应用图片数量统一为十张，上传字节沿用现有更严格约束并同时满足外部限制。张数放宽不改变单图字节、像素、整请求资源限制和上下文 token 预算。

这些值集中在 ImageGenerationProperties，不能在 Controller、setter、前端分别硬编码。服务端校验实际格式、解码尺寸、总像素、multipart 总体积及 prompt 长度；前端能力接口只用于预检和展示。提示词超限明确报错，不截断编号或末尾摘要。

输出允许的 64 MiB 与现有 10 MiB 输入资产限制不同，必须分开处理：

- 生成原件按输出限制验证、解码并保存到同一 assets 仓库，保留真实输出原图。
- 生图时按第 5.6 节用途准备 modelInput；底图和身份图必须仍为原件，超出服务限制时明确不可用，不能自动降级为派生版本。其他参考图可按需要等比例缩小和压缩；不覆盖原图。
- 派生版本仍属于同一资产，记录 sourceSha256、自身哈希、MIME、尺寸、字节；复用现有资产校验、哈希与缓存能力。
- 生图输入准备先预留底图和身份原图的像素及字节，再按剩余总预算确定其他参考图尺寸；仅对辅助参考做等比例缩小和编码，不补图、不裁掉主体。
- 正文的上传图继续沿用现有原图规则。未来生成原件可能大于当前聊天缓存的单图字节／像素限制，此时允许单独准备合规的 LLM 查看版本，不能让一张大生成图使整个候选预热失败。prepareChatInputs() 与生图用途策略分开，不能据此给生图底图或身份图换用压缩版本。
- 目录区分原件元信息和实际 modelInput 元信息。服务端缓存、token 估算和 validateCatalog() 按实际传输版本校验，不能拿派生哈希冒充原件哈希。
- 同一派生版本命中缓存时不重传；传给外部服务的版本由实际接口要求每次重新提交。提示词编号不随版本转换变化。

这是兼容现有资产与输入边界所必需的扩展，不另建图片存储系统。生成原图不会因为大于 10 MiB 被静默丢弃；无法得到满足限制的可读输入时，生图步骤明确失败。

### 10.3 超时与错误

外部调用读取超时建议 1800 秒，连接超时复用现有 10 秒。生图任务使用独立总截止时间，须覆盖外部调用及校验传输，不能沿用聊天任务的 600 秒截止时间。

成功响应必须校验状态、Content-Type、完整字节、PNG 格式、解码及输出资源限制；读到部分数据不能算成功。响应使用有界流读取，达到输出上限即中断。输出的最大像素数与解码内存预算也集中配置，并在分配像素前检查，不能只限制 PNG 压缩字节数。

| 外部错误 | 应用处理 |
| --- | --- |
| 400、413、INVALID_IMAGE | 输入错误，显示具体原因 |
| 401 | 配置鉴权错误，不提示用户修改聊天内容 |
| 429 QUEUE_FULL／MEMORY_BUSY | 服务繁忙，用户可稍后主动重试 |
| NOT_READY、COMFY_UNAVAILABLE 等 | 服务不可用 |
| EXECUTION_FAILED、MISSING_OUTPUT、INVALID_OUTPUT 等 | 生成失败 |
| QUEUE_TIMEOUT、EXECUTION_TIMEOUT、网络超时 | 区分远端明确失败与本地结果未知 |
| 代理 HTML／非 JSON 错误 | 按 HTTP 状态报告，不能强行按 JSON 解析 |

保存远端 request_id 便于定位，但不能把它当可查询任务 ID。超时、响应丢失或进程重启后不自动重新生图。日志只记录任务、错误码、耗时和计量，不记录 Token、原图二进制、Base64 或完整生成内容。

## 11. 独立生图任务与应用接口

新增 SceneImageTaskService，使用独立并发名额，第一版最多一个活跃生图任务，本地不另建长等待队列。外部等待仍可能发生，不伪造进度百分比。

| 应用接口 | 行为 |
| --- | --- |
| POST /api/scene-images | 提交客户端分配的 runId、冻结计划、角色快照及有序资产引用；返回任务快照 |
| GET /api/scene-images/{runId}/events | 先完整快照，再推送 revision 递增的任务状态 |
| GET /api/scene-images/{runId}/result | 成功后读取 PNG 原始字节 |
| POST /api/scene-images/{runId}/cancel | 取消本地工作并尽力关闭上游连接 |
| POST /api/scene-images/{runId}/ack | 浏览器保存终态后释放结果，重复确认成功 |

前端完整提供计划，不能只提交本地 planId 让无状态后端猜上下文。入口验证角色照片绑定、来源引用、顺序、数量、指纹及输入版本；后端不声称能独立认证浏览器数据库所有权，沿用当前客户端作用域与请求一致性边界。

任务生命周期：

1. 点击时校验本地计划来源版本，补齐最终参考图；此前聊天任务对图片缓存的占用可能已经释放，不能假设它们仍在缓存。
2. 后端在准入时预留结果额度、校验并 pin 参考图，再开启独立虚拟线程调用服务。
3. 同 runId、同请求指纹只返回或订阅原任务；同 runId、不同指纹返回冲突。
4. SSE 断开或切换会话不取消上游生图；显式停止才尽力关闭连接。任务不依赖浏览器请求的生命周期。
5. 成功后保留受配额保护的短期 PNG 结果，状态快照不嵌入二进制。
6. 浏览器下载 PNG，在事务外完成校验和缩略图准备，再原子保存资产与生成引用，之后 ACK。
7. 本地保存失败不 ACK；恢复只下载同一结果。浏览器已经落库但 ACK 响应丢失时，不重新保存或重新生成。
8. 终态失败在本地保存错误后 ACK。未知任务或结果过期显示不可恢复，明确保留本地计划。

结果缓存单任务额度必须容纳最大输出和元信息，不能直接复用聊天的“64 MiB 除以 32”额度。总结果容量、任务数量、保留时间和超时分别集中配置，满额拒绝新任务，不提前丢弃未到期结果。生成完成即释放输入占用和执行材料，仅保留结果及必要元信息。

仅图片数据临时驻留后端；后端重启会丢失任务与尚未取回的结果。远端没有查询接口，应用不能提供超出这一边界的恢复承诺。取消只说明应用停止等待并尝试终止，不能保证远端推理已经停止。

## 12. 生成图如何保存和复用

1. 新增 saveGeneratedImage()，复用资产解码、哈希去重、imgN 分配、缩略图和事务工具，不复用“用户上传草稿”入口。
2. 完整 PNG 与成功生成记录在同一事务建立引用，避免资产已入库但尚无引用而被回收。
3. 按实际计划保存 prompt、summary、target、参考清单和来源版本，不在消息 text 中插入“用户上传了图片”。
4. 前端从 sceneGenerations 投影出回复下方的图片卡片，使用现有 Object URL 展示机制，不修改正文消息检查点。
5. 后续 buildCatalog() 按本会话和发送快照来源 seq 收集生成图，提供 generationDescription；选择时仍实际加载原图或合规 modelInput。
6. 一轮正在生成期间到达的新结果，不改变已经冻结的选图材料和提示词；从下一轮开始参与候选。
7. 为生成任务单独保存输入使用关系，不把“生图服务使用过”混写成“正文 LLM 看过”。扩展 imageUsages 的使用类型或在生成记录中引用同一清单。
8. collectUnreferenced() 同时扫描计划、生成结果、在途任务、角色快照、草稿、观察与既有使用记录。删除会话统一删除对应计划与生成关系，再回收无引用资产。
9. 图库显示上传／生成出处、生成摘要来源、关联回复和否定状态；用户上传顺序保持原义。

## 13. 前端交互与恢复

- 回复下增加默认折叠的“剧情图”卡片，提示词可在折叠区域内持续流式更新。
- 提示词 ready 后显示生成按钮；unavailable、invalid 分别显示缺少条件或协议错误，正文照常可读。
- 显示参考图缩略图、用途和编辑底图，方便用户理解当前画面来源；不在普通角色台词中暴露任务字段。
- 生图请求不设置现有聊天 activeSessionId，不复用聊天 AbortController，不使输入框进入禁用状态。
- 生图按钮对同一计划运行时禁用；成功后展示图片，另设“重新生成”和“此图有误”操作。
- 重新生成分配新 runId，保留原计划和替代关系；不会因网络重连自动触发。
- 新页面加载恢复生图任务句柄，订阅和取回结果，不自动调用编辑 API。

- 复用现有同源代理转发 JSON、SSE 和二进制；核查外层代理的空闲超时与 PNG 下载上限，不给远端 Token 添加浏览器透传入口。

## 15. 数据库与协议升级

实施时 IndexedDB 从 v8 升至 v9，新增两个仓库、索引与 Session 视觉状态默认值，并为既有资产初始化 creationOrigin=uploaded。当前项目此前尚无生图来源，不需要猜测旧资产是否由外部模型生成。

现有 upgrade() 会删除所有仓库。必须改为按 oldVersion 执行明确的升级：已有 v8 数据原地补字段和新增仓库，不清空角色、会话或原图。保留现有更早版本的重建政策，不编造旧格式兼容层。

备份由 v9 升至 v10，只接受新协议，按项目规则不长期保留旧 DTO、构造器或双套运行分支。原件只导出一次；派生输入可以重建，备份允许不导出派生字节，但必须保留完整原件与所有业务引用。

不恢复已导出的远端任务句柄。成功结果和失败记录可恢复；导出时仍在运行的生成记录导入后标记 unknown，不宣称任务仍在服务器执行，也不自动重试。待整理任务随新快照协议升级，前后端同步发布。

## 16. 性能与模型调用预算

- 保持当前通常一次选图、一次流式正文、一次状态整理；没有候选时继续跳过选图。已有目录过大时沿用分批和最多一次纠错，不声称任何场景都固定三次调用。
- 不增加视觉状态解析 Agent、提示词扩写模型、生成图 caption 模型或质量检查模型。
- 首次上传图在既有整理调用中建立观察；后续仅需状态整理时不再附同一图，降低视觉输入成本。
- 生成摘要在主模型输出时已经完成，成功回调只保存数据。
- 正文前沿用当前“候选图缓存预热”，明确它可能补传全部缓存未命中的候选，十张限制只约束应用实际模型输入。
- 第一版不重写为选图后再向浏览器取图的双阶段聊天协议；后续若候选预热成为瓶颈，再单独设计保持后台可恢复性的传输优化。
- 实际生图只读取和上传最终清单；每次向外部服务重新提交这些文件是当前接口要求，不能用内容哈希替代上传。
- 新画面材料与旧画面摘要按现有辅助预算裁减；不要每轮重复传递历史完整提示词。身份绑定、实际参考清单和本轮明确视觉要求不能被静默裁掉。

## 17. 实施顺序

1. 先修正观察目标集：普通聊天与手动重试统一策略，覆盖新上传必选、历史观察复用与版本不变。
2. 扩展来源、视觉状态、描述类型和本地仓库；补齐备份、来源校验与引用回收。
3. 扩展文字选图材料，接入成功生成图片目录与连续性信息。
4. 接入主模型画面尾部协议、中文分层提示词及前端流式折叠卡片；此时可先验证计划而不调用生图服务。
5. 接入 QwenImageClient、按用途准备原图／辅助压缩版本、独立任务、二进制取回和原子保存。
6. 完成迟到结果、重生成、否定、恢复和跨轮连续性的集成测试，再按实际服务做手动验收。

## 18. 验收与测试

自动化测试优先覆盖入口行为、请求载荷与持久结果，不重复测试内层相同条件。使用本地 HTTP 夹具验证生图接口，不让默认测试访问内网 GPU 服务。

| 场景 | 必须验证的结果 |
| --- | --- |
| 首轮只上传新图、无摘要 | 跳过不必要历史选图，新图字节进入正文，整理首次观察 |
| 纯文字且无候选 | 不新增选图或视觉分析调用 |
| 历史上传图没有观察 | 可按上传语义选入，正文收到真实图，整理首次建立观察 |
| 上一轮已观察图再次选中 | 正文仍能看图，整理请求不再附它，原观察版本不变 |
| 已观察图片再次上传 | 正文必选，真实来源保留，不重复整理 |
| 首次角色照片 | 正文与首次观察仍正确；后续生图始终携带身份文件 |
| 生成图没有 observation | 依靠生成描述进入候选，不触发整理或压缩补做观察 |
| 只有未完成计划／失败生成 | 不伪造图片目录项或资产 |
| 普通聊天 | 可以输出折叠提示词，但没有外部生图调用 |
| 用户点击生成 | 独立任务实际调用 multipart 接口 |
| 参考图顺序 | 文件、冻结清单和 <imageN> 完全一致，第一张为正确编辑目标 |
| 只有身份图 | 只上传一张，没有占位或不存在的编号 |
| 换装但不生图 | visualChanges 提交新服装，下一轮不被旧生成摘要覆盖 |
| 仅要求图片换装 | target 改变，剧情 visualState 不被无依据改写 |
| 换地点保留服装 | 背景更新，衣服按当前状态继承 |
| 精确复杂服装／特定房间 | 按需增加对应参考，普通场景不凑满十张 |
| 被否定的生成图 | 其生成来源不再当连续性参考，身份锚点不变 |
| 生成摘要与图片不符 | 保持“未核实”来源；正文实际读图后可拒绝，不能回写虚假观察 |
| 超限或引用错误提示词 | 生图计划无效，正文与状态整理不受影响 |
| 图像生成与状态整理重叠 | 不占 ModelGate，不等待图片才继续整理 |
| 老图迟到 | 关联原回复，不修改新状态或正文 checkpointVersion |
| 双击与 SSE 重订阅 | 同 runId 只提交一次外部请求 |
| 本地保存失败／ACK 丢失 | 取回同一结果，不重新生图，资产与关系幂等 |
| 超时、429、401、错误 JSON／HTML | 错误分类正确，没有把错误正文保存成图片 |
| 生图底图和身份图 | 传输哈希与原件一致；同图兼具两种用途只传一次 |
| 辅助参考压缩 | 服装细节使用合适压缩图，粗略环境／姿态可用缩略图，参考顺序与编号不变 |
| 原图超出服务输入限制 | 底图或身份原图明确不可用，不静默压缩或换缩略图 |
| 输出超过聊天单图上限 | 原件完整保存，正文可读合规查看版本；作为生图辅助参考可压缩，作为底图或身份图仍必须校验并使用原件 |
| 缺少身份图／必需参考原件 | 明确不能生图，正常聊天沿用现有缺图规则 |
| 多会话与哈希去重 | 无跨会话私有摘要泄漏，同资产可以保留多个真实来源 |
| 数据库升级、备份及删除 | v8 数据保留，完整恢复生成关系，不清理仍被引用原图 |
