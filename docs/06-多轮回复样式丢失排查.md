# 多轮回复样式丢失排查

日期：2026-10-21。

## 已确认的行为

- 前端 `chatContext` 原先通过 `plainText` 回传角色历史，只有正文，没有 `[台词]` / `[描写]` 标记。系统提示词却要求所有输出行使用这些标记，历史示例与协议不一致。
- 后端 `SegmentStreamParser` 只通过行首标记确定类型。无标记正文保留为 `narration`，即使语义上是台词，也不会猜测类型。因此模型整条回复漏标记时，前端会统一显示成描写。
- 前端根据 `segments.kind` 选择渲染器，没有随轮数切换样式的逻辑。桌面、手机各四轮并在中途刷新，带正确类型的回复始终正常区分样式。

历史示例丢失标记是确定的协议问题，可能诱导模型省略标记；但没有截图对应的原始请求和模型输出，不能认定它就是该次问题的唯一原因。

## 真实模型对比

使用后端配置的 LLM 地址、模型和凭证，流式读取模型原始 `delta.content`。系统提示词由项目实际 `PromptBuilder` 生成，设置为「详细 + 场景推进」，温度 0.8，输出上限 8192 tokens。使用参考截图构造的李白与奖状场景，没有使用原会话或图片。

主要对比各连续十轮：包含开场描写，历史只保留最近二十条；旧路径模拟解析后合并同类型增量、再用 `plainText` 拼接的历史，新路径逐行恢复类型标记。

| 历史回传方式 | 回复数 | 非空正文行 | 有合法行首标记的行 |
| --- | ---: | ---: | ---: |
| 旧路径：纯正文 | 10 | 146 | 146 |
| 新路径：恢复类型标记 | 10 | 205 | 205 |

这组实测没有复现漏标记，不能据此声称已经证明因果关系或模型以后一定遵守协议。此前另做过各六轮的初步对比，也没有出现非空正文漏标记；旧路径有一次模型正常结束但没有返回正文，这与截图的整段纯文本现象不同。

临时探测脚本、请求消息和模型原始输出保存在 `/tmp/roleplay-format-diagnosis/`；未将凭证写入这些文件。

## 修改

- `frontend/lib/chat/context.ts`：按保存的 `kind` 恢复每个非空正文行的标记，包括同类型合并段内的多行；较早原文与近期历史使用同一序列化方式。中断说明标为描写，用户原文保持原样。
- `SegmentStreamParser`：遇到无标记正文时，每条回复记录一次告警「模型回复未遵循分段协议」，不记录正文。继续保留已经收到的内容。
- 展示和复制仍使用原有正文；不改写本地已保存的段落。已被归为描写的旧回复无法仅凭现存类型恢复其中的台词。

## 验证与再次定位

- `mvn test`：44 个测试通过。
- 前端 `npm test`：25 个测试通过；`npm run typecheck` 通过。
- 新增浏览器回归：桌面和手机各四轮，核对发出的历史、两类段落样式和中途刷新，两个用例通过。为避开已有开发服务，测试使用临时副本及 webpack 开发服务器。

后端告警需要在加载新代码的服务中生效。再次出现时，检查同次回复的 SSE `delta.kind` 和服务端日志：出现上述告警表示模型输出存在无标记正文；若 SSE 已含 `dialogue` 而对应正文没有背景，再检查前端渲染。没有告警也不能排除模型把台词错误标成 `[描写]`，这种语义误标需要核对具体正文。
