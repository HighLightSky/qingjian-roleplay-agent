# 后端编排、图片缓存与恢复

`backend-dispatch` 的当前生成链路以本文为准，替代 08、09 中由前端选图和自动补做整理的调用组织。

## 数据与调用边界

长期数据仍在浏览器 IndexedDB。每轮前端读取当前角色、剧情、记忆、目标、摘要和未摘要历史，完成预算预检及必要的历史压缩，再提交完整上下文。后端不维护会话数据库或跨轮上下文缓存。

浏览器数据库仍名为 `roleplay-agent`，版本为 v10。v8、v9 在单个升级事务内原地迁移，保留原图及全部业务记录；v7 及更早版本中止升级并保留原库，禁止删库重建。新备份为 v11，导入支持 v9、v10 入口转换；备份导入不恢复服务器任务句柄。详见 [开发与迁移计划](./15-剧情图开发与数据迁移计划.md)。

1. 前端按所有候选图、角色照片和本轮附件的 SHA-256 查询缓存，补传缺失的原图。
2. `POST /api/chat` 一次提交任务 ID、完整 context、本轮用户和正文消息的 ID/序号/时间，以及 `images: [{assetId, sha256}]`。外部请求不携带原图 Base64 或预生成选图计划。
3. 后端串行执行选图、流式正文、本轮状态整理。没有候选时跳过选图模型调用；只有非空且正常结束的正文触发整理。
4. 阶段及结果通过同一 SSE 返回。正文可以先落库，整理随后以领域版本和来源版本校验后原子提交。
5. 前端保存全部终态后 ACK，后端删除任务结果。

剧情图使用独立任务名额及另一条连接取消，页面离开和切换会话均不会取消生图；参见 [剧情图方案](./14-剧情图生成与视觉上下文方案.md)。聊天链路全局一个模型任务名额，整轮持有到整理结束。独立压缩和手动整理也使用同一名额，冲突返回 `409 MODEL_BUSY`。只读预算计数不占生成名额。

## 接口与事件

- `POST /api/images/missing`：`{hashes}`，返回 `{missing}`。
- `PUT /api/images/{sha256}`：二进制原图，上传时检查真实格式、体积、像素、可解码性和哈希。
- `POST /api/images/cache/stats`：`{hashes}`，返回 `{imageCount, bytes, inUseImageCount, inUseBytes}`。
- `POST /api/images/cache/clear`：`{hashes}`，返回 `{releasedImageCount, releasedBytes}`；目标中有原图被任务占用时返回 `409 IMAGE_IN_USE`，整次手动清理不执行。
- `POST /api/chat`：启动或幂等订阅同一任务，返回 SSE。
- `GET /api/chat/{runId}/events`：先返回完整快照，再推送后续增量。
- `POST /api/chat/{runId}/cancel`：显式取消上游请求，等待任务退出。
- `POST /api/chat/{runId}/ack`：仅终态可以确认删除，重复确认成功。
- `POST /api/state/update`：仅最新失败步骤手动重试，正文材料放在 `request`，图片缓存引用放在 `images`。
- `POST /api/validate/character`、`POST /api/validate/state`：人工编辑落库前复用服务端校验。

首事件 `snapshot` 是完整快照；后续事件以 `{revision,value}` 封装，包含 `stage/context/delta/image_prompt_delta/image_prompt_done/image_prompt_error/body_done/state_result/done`。`stage` 包含阶段名、状态、错误，选图阶段同时携带 plan。恢复快照替换已有正文，后续递增序号避免重复追加；快照捕获和订阅注册在同一同步边界内完成。

SSE 断开不取消任务。隐藏页面、切换应用、刷新和断网后可重新订阅；主动切换角色/会话或点击停止才显式取消。初次响应丢失后查询已分配任务 ID，不自动再创建模型调用。应用启动恢复选中会话不触发取消。

异步响应不可用（`AsyncRequestNotUsableException`）单独处理，不记录为模型失败，也不向失效响应写入错误 JSON。SSE 写入失败后的连接收尾交由 Spring 与 Servlet 容器完成，发送线程仅关闭本地订阅；实际模型调用错误仍按原有规则返回。

正文、整理结果以原有消息/操作 ID 幂等落库。事务失败不 ACK，保留任务元数据，下次恢复只重新取得同一结果。后台不存在或结果过期时保留本地检查点，明确显示不可恢复，不自动重新生成。

## 内存与回收

配置统一放在 `roleplay.dispatch`，清理扫描默认每 60 秒执行一次，访问也检查到期。

| 对象 | 默认限制与回收 |
| --- | --- |
| 图片 | 512 MiB，空闲 30 分钟过期，上传后绝对期限 2 小时；读取不续绝对期限 |
| 图片占用 | 活跃任务持有引用，不被容量淘汰；到期后不能被新任务使用，占用任务结束时释放 |
| 执行材料 | 仅存在于运行任务，终态立即释放上下文和原图使用引用 |
| 运行任务 | 总截止时间 10 分钟；每次模型调用还有独立超时，取消会中断请求并关闭流 |
| 待确认结果 | 最多 32 个、合计 64 MiB，按任务数量均分结果额度；终态后保留最多 2 小时，读取不续期 |
| 结果删除 | ACK 立即删除，未确认结果到期删除；满额拒绝新任务，不提前淘汰未到期结果 |

图片命中不重置上传时间；缓存只存实际传输图片字节及已验证元信息（包括生成图的合规 LLM 查看版本），不存会话来源或视觉观察。`img1` 等编号只在请求材料中使用，缓存键为内容哈希，因此不同浏览器编号相同也不会串图。

缓存明细和释放接口仅操作请求哈希，不返回其他浏览器的图片目录或后端全量用量。前端提交本地资产表的全部哈希；接口在共同入口归一化空集合、校验集合上限和 SHA-256，并去重。超过现有单集合 10000 项限制时明确报错，不拆分为可能部分成功的手动清理。

明细先回收过期且未被占用的条目，过期但仍被任务持有的条目继续计入。统计按唯一哈希计算原图字节数组长度，不代表 JVM 总内存，也不更新访问时间。检查占用和删除在图片缓存的同一个同步边界中完成；存在任一占用目标时拒绝全部手动删除。未命中和重复释放均返回零张、零字节。释放不操作任务结果缓存或浏览器原图；下一轮仍通过现有 missing 和上传接口补齐。不同浏览器持有同一哈希时共享同一缓存条目。

图片到期但仍被任务使用时，最多额外保留一个任务执行期限。后端所有缓存均不落盘，重启会丢失原图和未确认结果；原图可以从本地补传，未保存的生成结果无法在重启后恢复。日志不新增原图或生成内容全文。

整理与挑图的专用输入、短编号、辅助预算和思考开关见 [辅助上下文与模型调用策略](./12-辅助上下文与模型调用策略.md)。

## 容量和整理规则

模型容量统一满足：`实际输入 token + 当前阶段输出预留 + 安全余量 <= 部署窗口`。窗口默认 193024，安全余量 1024；正文/整理输出预留 8192，选图 4096。选图分批同样按 token 判断。图片 token 仍明确为估算。

请求体 64 MiB、单集合 10000 项属于资源保护。自由文本不再使用 2000/300/600 字符上限或 200 万字符总容量；必需字段、协议格式、枚举、来源和版本继续校验。宏观、简短的剧情和目标表达仍由提示词要求。

压缩保留在前端预处理，通过预算接口保守预留候选图空间，选图后后端再校验实际请求。上传图片缺少观察时，压缩可按模型图片数量与 token 预算直接读取缓存原图，不要求补做旧整理；生成图使用未经核实的生成要求摘要，不补做观察。

每轮只整理本轮。发送前、启动和切换会话均不自动补做。最新失败步骤可手动重试，新一轮整理开始后旧待办失效、旧操作保留但不能重试。整理失败不改变正文终态，不阻塞下一轮。结构或引用错误继续最多纠正一次；连接错误不自动重试。迟到或过期结果不能覆盖人工编辑。

状态整理输出未正常结束时，服务端日志与返回的错误详情包含实际 `finish_reason`、本次请求的输出 token 上限、上游报告的输入/输出/总 token 用量以及已返回正文字符数，不包含生成内容。`length` 明确提示模型因长度限制停止生成；缺少结束标记或用量时明确标为上游未提供，不推断为长度截断或零用量。

正文生成区分模型异常结束与 `stop` 但有效正文为空（包括仅返回空白或类型标记）。两者均保留正文结束原因与用量，通过 SSE 返回具体原因并记录不含正文的诊断日志，不触发状态整理。后台任务的非取消异常另外记录任务 ID、失败阶段与异常类型；异常由任务捕获，不会经过 Controller 的全局异常处理器。

前端在失败的回复位置以醒目的提示区分空正文与长度截断，完整显示诊断信息和任务 ID，并说明本轮未进行状态整理。错误随消息保存，重新打开会话仍能查看；已有部分正文继续保留。

## 原图缺失的显式跳过

历史聊天附件或会话角色照片的 IndexedDB 资产记录不存在时，前端保留原消息、照片快照和观察，图片目录返回可用的 `assetCatalog` 与缺失的 `missingAssets`。缺失项仅包含 `assetId/sources/observation`，不填充哈希、尺寸或字节；每次读取重新计算可用性，恢复原件后自动回到可用目录。缺图处理不改变数据库结构或重建数据。

后端共同入口校验两个集合的总量、唯一编号、来源位置、照片快照和观察版本；历史图片及照片来源必须属于其中一个集合。`missingAssets` 的缺省值在边界归一为空数组。本轮新附件不能声明为缺失，普通发送与失败重发在事务写入消息前共用原件存在性检查，失败保留草稿与已有消息。

缺图不进入选图目录、缓存补传、图片名额及图片 token 估算。正文、辅助选图与整理材料明确说明“原件缺失，已跳过，本次无法复核”；已有观察仅作为有损记录提供，整理不能为缺图生成新观察。历史压缩保留真实图片编号、观察版本，并对每张涉及的缺图保留 `[原图缺失：imgN]` 标记。图片位置与上传顺序仍计入缺图，后续新图的 `uploadIndex` 不因原件丢失而改变。

最新失败整理手动重试时重新构建目录，移除旧计划中已缺失的历史选图；该任务本轮输入的原图若缺失则此次重试失败，不阻止下一轮发送。数据库读取异常、原图损坏和哈希不符仍明确报错，不归为可跳过的缺图。

会话持续列出跳过编号，历史附件、角色照片及操作中的图片预览显示缺失状态。本地数据明细照常统计已保存记录和真实图片容量，缺图不计入图片数量及图片字节，另外按资产编号去重显示来源；正常资产的共享归属与计量规则不变。完整备份仍要求所有被引用的原件存在，不接受以缺失声明代替原图。

历史问题定位：后端上传失败本身不会删除浏览器原件。旧版附件同步可能用准备中的附件列表覆盖草稿引用并触发回收；该路径已在多附件草稿修复中移除。普通发送过去缺少原件检查，可能进一步将悬空引用写入历史。使用内存数据库可复现这条致错链，但没有事故时的数据与日志，不能将它断言为每次缺图的唯一来源。
