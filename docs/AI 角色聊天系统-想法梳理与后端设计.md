# AI 角色聊天系统：想法梳理与后端设计

> 本文是待实现的设计，不代表当前代码已经具备这些功能。目标是用 Java 逐步完成一个可以在命令行中体验的角色聊天系统，之后再接入现成的聊天前端。项目不引入数据库，也不在服务端长期保存用户数据；可继续对话的存档由用户自己保管。

## 1. 我们要做什么

用户可以创建一个拥有身份、性格、背景和说话风格的虚拟角色，与其持续聊天、共同推进故事，也可以发送图片让角色结合图片作出回应。

角色的回复同时包含两种内容：

- **台词**：角色对用户说的话。
- **叙述**：角色的动作、神态，以及当前环境和故事情节的描述。

系统在本次使用期间记录聊天历史和必要的记忆，结束时将完整缓存包交给用户并清理服务端临时数据。下次用户导入缓存包，角色就能接上之前的故事。

例如：

```text
用户：我推开旅馆的门，把一张地图放到桌上。[附带地图图片]

角色：
（林溪抬起头，目光落在地图右上角的红色标记上。窗外的雨声渐渐密集。）
“你也发现这座塔了？我昨天在那里见过同样的符号。”
（她挪开桌上的烛台，为地图腾出位置。）
```

这里的“Agent”先理解为“有角色设定、上下文和记忆的聊天角色”。第一版用一次主要模型调用生成一条回复，不引入自主规划、工具链或多个 Agent 协作。

## 2. 第一版的范围

| 功能 | 第一版怎么做 |
| --- | --- |
| 自定义角色 | 创建、查看和修改角色的基本设定 |
| 多轮聊天 | 一个会话绑定一个角色，保存双方消息 |
| 角色记忆 | 最近聊天原文 + 较早剧情摘要 + 用户手动维护的重要记忆 |
| 图片输入 | 从本地上传图片，再将文字和图片一起交给支持视觉的模型 |
| 角色输出 | 使用一段文本，混合台词、动作和场景叙述 |
| 使用入口 | Java `App` 提供命令行交互 |
| 数据保存 | 运行期间使用临时缓存文件，结束时导出给用户并清理；下次导入继续 |
| 隐私原则 | 用户持有长期存档，服务端不建立用户数据存储库 |
| 前端对接 | 先确定业务接口和未来 HTTP 接口，前端后续实现 |

暂不做登录、多用户权限、多人群聊、语音、图片生成、向量数据库、复杂工作流和微服务。第一版按本机单用户、单进程使用设计。

### 数据归属与“服务端零存储”的含义

本项目的核心约束是：**长期数据保存在用户手中，服务端仅在处理期间临时持有数据，使用结束后清理。** 不引入数据库，也不将本地文件存档作为服务端长期存储方案。

运行期间既然会创建缓存文件，就仍然存在临时落盘。因此这里的“零存储”准确指**服务端不长期留存用户数据**，不是“请求处理时完全不接触或不写入用户数据”。用户的角色、聊天、记忆、摘要和图片都遵守同一规则。

分两个阶段实现：

| 阶段 | 用户数据如何保存 | 服务端承担什么 |
| --- | --- | --- |
| 当前命令行版 | 结束时导出完整缓存包到用户指定位置，下次手动导入 | 本次运行的临时缓存、模型调用和导入导出 |
| 后续浏览器版 | 由浏览器本地存储维护角色、历史、记忆和图片，并提供文件导入导出 | 逐步改为接收本轮所需上下文、返回回复与更新结果，不保存跨请求的会话状态 |

命令行版与用户运行在同一台机器时，也区分“程序管理的临时目录”和“用户指定的导出文件”。清理前者，不删除用户保管的文件。没有导出的最新进度，在临时缓存被清理后无法由服务端找回。

“图片功能”在本文中指**发送图片和理解图片**。角色暂时只输出文字；如果以后需要角色画图，再单独增加图片生成能力。

## 3. 先分清几个概念

### 3.1 角色：他是谁

角色是可复用的设定，建议包含以下字段：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `id` | 角色标识，由后端生成 | `char_001` |
| `name` | 名称 | 林溪 |
| `description` | 身份和背景 | 山间旅馆的老板，曾经是探险家 |
| `personality` | 性格 | 谨慎、好奇、愿意帮助熟悉的人 |
| `speakingStyle` | 说话风格 | 简短自然，偶尔带一点幽默 |
| `worldSetting` | 世界观 | 一座被迷雾包围的山城 |
| `openingScene` | 开场场景 | 雨夜，用户走进旅馆 |

用户填写的是角色资料，后端负责将这些资料组合成模型提示词，用户无需直接编写整段系统提示词。

### 3.2 会话：这次故事发生了什么

一个会话是一条独立的故事线，绑定一个角色。同一个角色可以开启多个会话，但各会话的消息、摘要和重要记忆互不共享。

例如，“林溪：旅馆初遇”和“林溪：废塔探险”是两个独立故事存档。**继续旧会话**会保留记忆；**新建会话**从新的开场开始。旧会话只能来自本次运行已创建的数据或用户导入的缓存包，不能依靠服务端长期检索。

会话保存 `id`、`characterId`、`title`、`createdAt`、`updatedAt` 和一份创建时的角色设定快照。修改角色资料影响之后新建的会话；已有会话沿用快照，避免故事中途突然换人设。

### 3.3 消息：用户和角色分别说了什么

一条消息至少包括：

- `id`、`sessionId`、`role`、`createdAt`。
- `text`：文字内容。
- `imageIds`：关联的图片标识列表，第一版最多一张。

`role` 在业务数据中只需要 `user` 和 `assistant`。系统提示词由后端临时构造，不作为用户聊天消息保存。

用户消息允许只有文字、只有图片，或图文一起发送；文字和图片不能同时为空。角色消息第一版只有文字。

### 3.4 记忆：下一次请求要带上哪些内容

保存聊天记录不等于模型自动记住了聊天。模型每次请求只能使用后端传入的上下文，后端需要决定哪些内容随请求一起发送。

第一版采用三层上下文：

| 类型 | 保存什么 | 如何维护 |
| --- | --- | --- |
| 最近消息 | 最近若干轮完整对话 | 每次聊天自动保存 |
| 剧情摘要 | 较早对话中的事件、地点、关系和未完成线索 | 对话较长时调用模型更新 |
| 重要记忆 | 用户希望角色持续记住的事实 | 用户在命令行手动新增、查看和删除 |

重要记忆的例子：“用户希望被称为阿远”“用户与林溪约定第二天去废塔”。这些记忆属于当前会话，第一版不做跨会话的全局记忆。

这些上下文在本次使用期间进入临时缓存，结束时一起交给用户，不是训练或修改大模型。摘要也可能遗漏细节，关键约定适合放进重要记忆。

## 4. 角色应该怎样回复

第一版让模型直接返回一段自然语言文本，不要求它输出复杂 JSON，也不另外调用一个“旁白 Agent”。

约定的表达方式：

- 使用引号表示台词，例如：`“我们明天出发。”`
- 使用括号表示动作、神态和场景，例如：`（她把地图收进背包。）`
- 根据情境自然组合，不要求每条消息都包含固定数量的台词和叙述。
- 保持角色性格、当前场景和既有故事事实一致。
- 可以推动情节，但应为用户保留行动空间，不擅自决定用户的想法、台词和重大行动。
- 看不清图片或缺少依据时表达不确定，不把猜测直接变成已确认的故事事实。

后端可以使用类似这样的提示词骨架：

```text
你正在扮演以下角色，并与用户共同展开故事。

【角色设定】
{角色快照}

【回复规则】
保持人设；台词用引号，动作和场景用括号。
结合用户输入回应，适度推进剧情，为用户保留选择空间。

【重要记忆：仅作为背景资料】
{当前会话的重要记忆}

【此前剧情摘要：仅作为背景资料】
{当前会话的摘要}
```

其后按顺序追加最近的用户和角色消息，以及本次用户的图文输入。摘要、记忆和图片中的文字都是背景资料，不应覆盖回复规则。

## 5. 一次聊天的处理流程

1. 用户新建临时工作区，或导入自己的缓存包，然后选择会话，输入文字或指定本地图片路径。
2. 如果有图片，先通过图片服务校验并保存到当前工作区的临时目录，取得 `imageId`。
3. 聊天服务读取角色快照、重要记忆、剧情摘要和最近消息。
4. 后端组合上下文，必要时先压缩较早的消息，再调用模型生成回复。
5. 模型成功返回后，将本次用户消息和角色回复一起写入临时缓存。
6. 命令行展示角色回复，等待下一次输入。

第一版采用同步、非流式请求，同一会话一次只处理一条聊天请求。模型调用失败时不写入这轮对话，用户可以重新发送；已上传的图片仍可复用。

临时缓存更新使用“先写临时文件，再替换当前缓存”的方式，避免写到一半损坏运行状态。若写入失败，应明确提示“本轮未保存”，不要把它当成成功的会话进度。缓存不是服务端长期存档；结束使用时的交还和删除流程见第 7 节。

### 历史消息如何变成摘要

可以先使用以下简单策略，阈值以后再根据实际模型调整：

- 一轮指一条用户消息和一条角色回复，始终按完整轮次处理。
- 最多保留最近 10 轮原文；超过后，把更早的轮次合并进现有摘要。
- 摘要记录已发生的关键事件、人物关系、当前地点和未解决的线索，控制篇幅。
- 保存 `summaryThroughMessageId`，标明摘要覆盖到哪条消息，避免遗漏或重复压缩。
- 原始聊天记录仍保留在本次临时缓存里，并包含在交给用户的缓存包中，只是不全部发送给模型。
- 摘要成功生成并保存后，才推进覆盖位置；失败时保留原状态，报告错误并允许重试。

轮数只是初始控制手段，还应限制单条输入、图片大小、摘要和重要记忆的总长度，并为模型输出预留上下文空间。具体限制集中放在配置中；超过预算时先压缩历史，仍超出则提示缩短输入。

## 6. 图片怎样接入

图片流程分为两步：**保存文件**和**将图片内容传给模型**。仅把图片路径作为普通文字发送，模型无法据此读取本地图片。

第一版的处理约定：

1. 命令行接收本地图片路径，由图片服务读取并校验实际格式。
2. 满足模型服务的限制即可。
3. 图片保存到当前工作区的临时目录，用后端生成的 `imageId` 关联消息，不把用户输入的文件名直接用作保存路径。
4. 模型适配层读取图片字节，按所接服务的多模态协议构造请求；例如在服务支持时使用内嵌图片数据。无需让模型服务访问本机路径。
5. 如果配置的模型不支持视觉，明确返回“不支持图片输入”，不要静默忽略图片。

图片原图不能保存在服务端。

图片消息的成功回复可以帮助后续摘要记录视觉信息；视觉信息仍以模型实际识别结果为准。**现有项目能完成文本调用，不代表当前接入的模型已经支持视觉，需要在图片阶段验证。**

## 7. 后端结构：先保持一个 Java 项目

当前项目已经有 `App`、`LLMClient`、`OpenAiClient` 和模型请求、响应对象，可以在此基础上逐步扩展。

建议保持下面的调用关系：

```text
App（命令行）                     未来的 HTTP Controller
       │                                  │
       └──────────── 业务 Service ──────────┘
                         │
           ┌─────────────┴─────────────┐
     RuntimeCache（临时缓存）     LLMClient（模型调用）
```

职责划分如下，开始实现时无需一次建齐所有类：

| 模块 | 主要职责 |
| --- | --- |
| `App` | 读取命令、展示结果，调用业务服务 |
| `CharacterService` | 创建、读取和修改角色 |
| `SessionService` | 创建会话、读取历史、维护重要记忆 |
| `ChatService` | 校验聊天输入、组织上下文、请求模型、保存本轮消息 |
| `ImageService` | 校验、保存和读取图片 |
| `RuntimeService` | 创建临时工作区、导入导出缓存包、结束与清理本次运行 |
| `RuntimeCache` | 在当前工作区内读写临时 JSON 和图片文件，不提供长期存档 |
| `LLMClient` | 统一模型调用接口，由适配实现处理服务协议 |

摘要生成和提示词拼接最初可以是 `ChatService` 的内部方法，变复杂后再拆分。API 地址、密钥、模型名称和上下文限制放进配置，密钥不写入代码、临时会话数据或导出包。

现有 `llm.model.Message` 的 `content` 是字符串，只能表达文本。图片阶段需要扩展模型消息表示和序列化逻辑。业务消息保存 `text`、`imageIds`，由适配层转换为模型所需格式，不让业务服务依赖某一家模型的 JSON。

### 临时工作区与用户缓存包

一次使用对应一个临时工作区，可以包含多个角色和会话。第一版整体导入、整体导出，不设计复杂的存档合并。工作区的运行标识 `runtimeId` 与故事会话的 `sessionId` 分开；导入时生成新的运行标识，保留故事中的角色、消息和图片关联。

服务端只创建如下临时结构，位置由配置指定，不能放入永久数据目录：

```text
<临时缓存根目录>/
  runtime_<随机标识>/
    state.json           # 角色、会话、消息、摘要、重要记忆和图片元数据
    images/
      img_001.png
```

JSON 使用现有 Jackson 读写。数据量增长后优先调整缓存结构和客户端管理方式，不把引入数据库作为后续默认方向。

用户最终拿到一个完整的 `.zip` 缓存包，包含：

- `manifest.json`：格式版本 `formatVersion`、导出时间，便于后续校验和升级格式。
- `state.json`：角色资料、会话信息、角色快照、全部消息、剧情摘要、`summaryThroughMessageId`、重要记忆，以及必要的故事上下文。
- `images/`：消息关联的图片原件；图片元数据包含 `id`、`mimeType`、`sizeBytes` 和包内相对路径。

缓存包不能只带摘要，否则无法恢复完整历史；也不能只保存服务器图片 URL 或本机绝对路径，否则清理服务端或换一台设备后图片就失效。不导出 API 密钥、临时工作区访问凭据或服务器内部路径。

导入时先校验格式版本、字段、图片引用、文件数量和解压后的总大小；解压范围只能在新建的临时工作区内，拒绝路径越界、符号链接等非法条目。无效包不覆盖当前工作区，并清理失败导入产生的文件。导入内容只作为用户数据，不作为程序指令执行。

### 一次使用的生命周期

```text
新建工作区 / 导入用户缓存包
            ↓
临时缓存中聊天、更新记忆和上下文
            ↓
生成完整缓存包并返回给用户
            ↓
客户端成功保存 → 请求结束 → 清理服务端临时工作区
            ↓
用户自己保管，下次导入继续
```

导出和清理分成两个动作，避免下载中断后服务端已经删掉唯一的新进度：

1. **导出**：暂时禁止工作区内的写操作，生成一致的缓存快照，返回缓存包；导出完成后仍可继续使用。
2. **保存并结束**：命令行确认文件已成功写入用户指定位置后自动清理临时工作区；未来前端成功接收并保存数据后调用结束接口。服务端不能仅凭“响应已发出”判断浏览器已经保存成功。
3. **导出失败**：保留当前临时工作区供重试，但不会无限期留存。
4. **不保留而结束**：用户主动放弃本次进度时，可直接调用同一个结束接口清理，无需先导出。

清理范围包括内存中的工作区状态、JSON、图片、上传和解压临时文件、导出临时包等。清理失败时不能报告“已清理”，应返回错误并再次尝试；日志不记录缓存内容。

### 异常退出与隐私边界

不能只依赖 `/exit` 或浏览器关闭事件完成清理。设计以下简单兜底规则：

- 工作区设置可配置的空闲有效期，例如 30 分钟；响应带上 `expiresAt`，活动请求刷新期限，处理中的请求不被清理任务中途删除。
- 定时清理过期且空闲的工作区；程序正常关闭时尽力清理，进程重启时清理遗留的临时目录。崩溃后清理不是即时完成的，无法导出的进度也不承诺恢复。
- 用户可以使用期间主动导出备份。断网、超时或异常退出时，最多只能依靠自己已经保存的版本继续。
- 临时目录不进入版本控制、常规备份或应用数据快照；请求体、回复、图片、摘要、导出包和访问凭据不写入日志、链路追踪或错误报告。日志只保留必要的状态和耗时等信息。

这里承诺的是应用侧不长期留存用户数据，不等于磁盘上的可验证安全擦除。模型调用仍需要把必要的文本和图片发送给配置的模型服务；该服务是否留存请求取决于其部署与配置，不能由本项目删除临时缓存来保证。

### 后续浏览器保存数据的方式

前端接入后，角色、聊天历史、记忆、摘要和图片可以保存在浏览器本地，例如使用 IndexedDB，并继续提供完整缓存包导入导出，方便备份和迁移设备。

目标流程是：浏览器读取当前会话状态 → 发送本轮所需的角色设定、记忆、摘要、最近消息和图片 → 后端调用模型并返回回复及必要的摘要更新 → 浏览器保存更新结果。上下文裁剪和预算检查仍由后端统一执行，不要求浏览器掌握全部模型调用规则。

达到这一阶段后，后端可以不再维护跨请求的工作区文件，只在请求处理期间使用内存或必要的短期临时文件，并在请求结束后释放。第一版的临时工作区接口用于命令行阶段，浏览器无状态接口后续再细化，不要求现在一次实现两套方案。

用户清理浏览器数据、使用无痕模式或更换设备时，本地进度可能丢失；需要依靠用户导出的包恢复，服务端没有可供找回的副本。“只在浏览器长期保存”也不代表数据不经过后端或模型服务。

## 8. 先确定业务接口，再接 HTTP

现阶段命令行直接调用 Java Service，不必为了命令行先启动 Web 服务。下面是计划提供的业务能力，不是当前已有的方法：

```java
RuntimeWorkspace createRuntime();
RuntimeWorkspace importRuntime(Path archivePath);
void exportRuntime(String runtimeId, Path targetPath);
void closeRuntime(String runtimeId);

Character createCharacter(CreateCharacterCommand command);
List<Character> listCharacters();
Character getCharacter(String characterId);
Character updateCharacter(String characterId, UpdateCharacterCommand command);

Session createSession(String characterId, String title);
List<SessionSummary> listSessions();
Session getSession(String sessionId);
List<ChatMessage> listMessages(String sessionId);

Memory addMemory(String sessionId, String content);
List<Memory> listMemories(String sessionId);
void deleteMemory(String sessionId, String memoryId);

ImageAsset uploadImage(Path localPath);
ChatReply chat(String sessionId, SendMessageCommand command);
```

这些方法分别属于上一节对应的 Service。`Character` 指业务角色类型，实现时可取名 `RoleCharacter`，避免与 `java.lang.Character` 混淆。角色、会话、记忆和图片操作都绑定当前临时工作区，列表方法也只列出其中的数据；这里省略重复的工作区参数，实现时通过参数或绑定工作区的服务实例明确传递。

`exportRuntime` 负责将缓存包可靠地写入用户指定文件，写入成功后才能由 `App` 调用 `closeRuntime`。导入只读取用户源文件，关闭工作区不删除导入源文件或已经导出的包。未来 HTTP 导出直接返回文件流，不允许客户端指定服务器文件路径。

`SendMessageCommand` 包含 `text` 和 `imageIds`；`ChatReply` 包含会话 ID、本次用户消息和角色回复。未来 HTTP 上传接收文件流，由入口层转换后复用图片服务的校验和保存逻辑。

### 未来 HTTP 接口草案

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/runtimes` | 创建临时工作区，返回运行标识和过期时间 |
| `POST` | `/api/runtimes/import` | 上传完整缓存包，恢复到新的临时工作区 |
| `POST` | `/api/runtimes/{id}/exports` | 返回当前完整缓存包，成功返回 `200`，不自动清理 |
| `DELETE` | `/api/runtimes/{id}` | 结束使用，清理临时工作区；客户端保存成功后调用，也可用于主动放弃 |
| `POST` | `/api/characters` | 创建角色 |
| `GET` | `/api/characters` | 列出当前工作区的角色 |
| `GET` | `/api/characters/{id}` | 获取角色详情 |
| `PUT` | `/api/characters/{id}` | 更新完整角色设定 |
| `POST` | `/api/sessions` | 根据角色创建会话 |
| `GET` | `/api/sessions` | 列出当前工作区的会话 |
| `GET` | `/api/sessions/{id}` | 获取会话信息，包括角色快照、摘要和重要记忆 |
| `GET` | `/api/sessions/{id}/messages` | 获取聊天历史 |
| `POST` | `/api/sessions/{id}/messages` | 发送图文消息并同步返回角色回复 |
| `GET` | `/api/sessions/{id}/memories` | 查看重要记忆 |
| `POST` | `/api/sessions/{id}/memories` | 新增重要记忆 |
| `DELETE` | `/api/sessions/{id}/memories/{memoryId}` | 删除重要记忆 |
| `POST` | `/api/images` | 通过 `multipart/form-data` 上传图片 |
| `GET` | `/api/images/{id}` | 读取图片，供未来前端展示 |

除创建和导入外，请求通过 `X-Runtime-Id` 携带当前运行标识；路径中的工作区 ID 也必须与其匹配。运行标识采用不可预测的随机值，作为临时访问凭据，不记录到日志或导出包中；角色、会话和图片必须属于该工作区。工作区清理或过期后，旧标识失效，不能再通过原会话或图片 ID 访问数据。

结束接口按幂等方式设计，同一运行的重复清理请求可以安全重试。过期工作区的业务请求返回 `410`，客户端提示重新导入自己保管的包。结束前由客户端等待正在处理的聊天完成，避免导出的状态遗漏最后一轮。

发送消息示例，`imageIds` 中的 ID 来自图片上传结果：

```http
POST /api/sessions/session_001/messages
Content-Type: application/json
X-Runtime-Id: <本次运行的随机标识>

{
  "text": "你能看出这张地图上的标记是什么意思吗？",
  "imageIds": ["img_001"]
}
```

成功响应示例：

```json
{
  "sessionId": "session_001",
  "userMessage": {
    "id": "msg_003",
    "role": "user",
    "text": "你能看出这张地图上的标记是什么意思吗？",
    "imageIds": ["img_001"]
  },
  "assistantMessage": {
    "id": "msg_004",
    "role": "assistant",
    "text": "（林溪将地图转向烛光。）“这个标记看起来像是废塔，不过我还不能确定。”",
    "imageIds": []
  }
}
```

示例省略时间等通用字段。创建资源返回 `201`，查询和聊天成功返回 `200`，删除成功返回 `204`。错误返回统一的 `code`、`message`，例如：

```json
{
  "code": "MODEL_UNAVAILABLE",
  "message": "模型服务暂时不可用，请稍后重试。"
}
```

基本错误包括：输入或缓存包无效（`400`）、角色／会话／图片不存在或不属于当前工作区（`404`）、工作区过期（`410`）、图片或导入包过大（`413`）、格式不支持（`415`）、模型调用失败（`502`）、模型超时（`504`）、临时缓存写入／导出／清理失败（`500`）。不支持视觉的配置作为明确的输入能力错误返回 `400`。

含有用户内容或访问凭据的 HTTP 响应设置 `Cache-Control: no-store`，部署时避免代理缓存这些响应。浏览器由前端显式保存数据，不依赖 HTTP 缓存留存聊天内容。

这些是应用自己的接口。以后选定聊天前端后，再根据其协议增加适配入口；现成前端不一定能直接调用这份接口，也未必自带角色和记忆管理界面。

## 9. 命令行的最小体验

命令只是交互草案，可以从菜单式输入开始，不必先开发复杂的命令解析器。

```text
/runtime new                  新建临时工作区（启动时也可默认创建）
/runtime import /path/save.zip 导入缓存包，建立新的临时工作区
/runtime export /path/save.zip 导出备份，继续使用当前工作区
/character create             按提示填写并保存角色
/character list               列出角色
/character edit char_001      修改角色资料
/session new char_001         创建并选中新会话，显示开场场景
/session list                 列出会话
/session use session_001      继续已有会话
/history                      查看当前会话历史
/memory list                  查看当前会话的重要记忆
/memory add 我希望被叫作阿远   添加重要记忆
/memory delete memory_001     删除重要记忆
/image /path/map.png          选择图片，可继续输入本次附言后发送
/exit /path/save.zip           导出成功后清理临时缓存并退出
/exit discard                 放弃未导出的进度，清理临时缓存并退出
```

选中会话后，直接输入普通文本就发送消息。启动时可新建临时工作区，也可导入用户保管的包，再选择其中的角色和会话。开场场景先作为会话中的初始角色消息写入临时缓存，后续一起参与上下文。

第一版一次只激活一个工作区，已有工作区时先导出并结束或主动放弃，再新建或导入，避免隐式覆盖进度。单独输入 `/exit` 时提示填写导出位置或明确选择放弃；导出失败留在当前程序中供重试，不宣称数据已交还或已清理。

## 10. 建议的实现顺序与验收方式

| 步骤 | 完成什么 | 如何判断完成 |
| --- | --- | --- |
| 1. 多轮文本聊天 | `App` 循环输入，累计用户和角色消息，通过已有 `LLMClient` 请求 | 先告诉模型一个名字，下一轮询问时能接上 |
| 2. 角色与会话 | 角色资料、角色快照、开场场景、创建和切换会话 | 同一角色可开启两个互不串历史的会话 |
| 3. 临时缓存与交还 | 工作区临时文件、完整包导入导出、结束及过期清理 | 导出并结束后临时目录消失；重新运行只有导入用户包后才能恢复；重启后清除异常残留 |
| 4. 简单记忆 | 手动重要记忆、较早对话摘要、上下文长度控制 | 触发摘要后仍记得关键约定，已删除的重要记忆不再作为独立记忆注入 |
| 5. 图片理解 | 图片临时保存、多模态消息适配、图片随包交还 | 图文和仅图片输入可用；导出并清理后，在新工作区导入仍能读取原图 |
| 6. HTTP 入口 | 在业务服务外增加 Controller，按草案提供接口 | 完成导入、聊天、下载缓存包、结束；旧运行标识不能再读取会话或图片 |

与隐私目标直接相关的验收还包括：导出失败时允许重试；非法导入不影响已有进度且不遗留解压文件；空闲超时后清理；清理失败明确报错；日志不包含对话、图片或缓存包内容。浏览器本地保存作为后续单独阶段验收，不在第一版实现前端。

删除重要记忆不会自动删除历史消息或摘要中的同一事实，也不等于角色会彻底忘记。第一版只承诺移除该条独立记忆；如需彻底清除一段故事背景，可以新建会话。

当前先落实本文的设计。实现时从第 1 步开始，前端改造在这些核心能力可用之后进行。
